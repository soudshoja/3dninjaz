<objective>
Wave 6 — Success Criterion 3 + TEN-02. The single most important property of the whole phase: prove, by TEST not reasoning, that on a ≥2-tenant dev fleet no singleton or cache can touch the wrong tenant — for READS and for a WRITE. Single-tenant dev CANNOT detect this class of bug (Pitfall 1 warning) — a second tenant is required to make leakage observable.

Purpose: TEN-02 ("no cross-tenant data ever returned") and SC3 (tenant A isolation + A's cookie rejected on B). The revision hardens two gaps: BOTH process-global caches must be cold-start-clean (store-settings AND whatsapp-settings — W6), and the battery must include an actual cross-tenant WRITE, not only reads (W7).

Output: a hand-provisioned second dev tenant, `TENANT_MODE=registry` on dev, and `.planning/phases/24-singleton-dissolution-sweep/24-ISOLATION.md` recording the battery.

NOTE: full end-to-end tenant provisioning (real domain, AutoSSL, create-tenant tooling) is Phase 28 — this plan needs only a hand-cloned second DB + registry rows + Host-header-based testing, sufficient to detect singleton/cache leakage.
</objective>

|----------|-------------|
| tenant A cookie ↔ tenant B domain | per-tenant Better Auth + per-tenant session table makes A's token meaningless on B (proven by test) |
| unknown Host ↔ any tenant | notFound() — never a default tenant (TEN-03, re-verified under the sweep) |
| process-global caches ↔ two tenants | cold-start ordering test proves BOTH the store-settings and whatsapp-settings cache keys are tenant-scoped (Pitfall 8 / W6) |
| tenant B write ↔ tenant A database | a guard-supplied tenant db writes only to its own DB — proven by a real order INSERT (W7) |
