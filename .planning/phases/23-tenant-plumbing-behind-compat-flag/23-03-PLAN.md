<objective>
Build the pool manager — lazy per-tenant mysql2 pools with the exact research-verified values (`connectionLimit: 3`, `maxIdle: 1`, `idleTimeout: 60_000`), plus the permanent platform pool singleton — and wire `TENANT_MODE` (default `single`) into `src/lib/db/index.ts` additively without disturbing a single existing call site. Record the fleet connection budget against the box's real `max_connections`.

Purpose: The naive retrofit (one `connectionLimit: 10` pool per tenant) exhausts MariaDB's ~151 connections at ~15 tenants and takes down the live store with it (PITFALLS.md Pitfall 2). The pool manager is the answer: aggressive idle shrink + a hard LRU cap. Under `TENANT_MODE=single` (the deployed default), the machinery must add ZERO connections — it reuses today's singleton pool as the one tenant's pool (23-PATTERNS.md § db/index.ts).

Output: `src/lib/tenant/pool-manager.ts` + tests, additive edits to `src/lib/db/index.ts`, mysql2 bumped to `^3.22.6`, DEPLOY-NOTES.md connection-budget section.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| registry DSN → mysql2 pool | Pools are built from `tenant.dsn` supplied by the registry — a wrong/attacker-influenced DSN opens the wrong DB |
| fleet of pools → single MariaDB instance | All tenant + platform pools share one MariaDB; over-provisioning takes down every tenant incl. the live store |
| compat flag → runtime behavior | `TENANT_MODE` decides whether Host-based routing or the legacy singleton path runs |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
