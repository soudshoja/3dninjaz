<objective>
Create the platform registry database and its Drizzle schema — the source of truth for tenant → DSN → domain resolution that every other Phase 23 module reads. This is the [BLOCKING] schema task: it defines the `Tenant` type the pool manager, registry, and context resolver all consume, and it physically stands up `ninjaz_platform_dev` with the `tenants` and `tenant_domains` tables.

Purpose: The platform DB is architecturally separate from every tenant DB (ARCHITECTURE.md system overview, rows 66-68). It stores **full `mysql://` DSNs** (not just DB names) so a tenant DB can later relocate to another server via a registry row update, never a schema change (the relocation escape hatch, ARCHITECTURE.md component table row 139).

Output: `src/lib/tenant/platform-schema.ts`, `scripts/phase23-migrate.cjs`, a live-applied `ninjaz_platform_dev` DB with both tables verified, and DEPLOY-NOTES.md recording the DB-creation ops step.

      id: varchar("id", { length: 36 }).primaryKey(),

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| migration script → live MariaDB | A CJS script with app-user credentials issues DDL against a real database on the shared box |
| registry rows → connection strings | `tenants.dsn` stores full `mysql://` DSNs — connection secrets at rest in the platform DB |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-23-01-01 | Tampering | phase23-migrate.cjs targeting the wrong DB | mitigate | Script targets `PLATFORM_DATABASE_URL` exclusively and never `CREATE DATABASE`; if the DB is absent it exits(1) with instructions rather than falling back to `DATABASE_URL` (the tenant DB). No path writes tenant-DB DDL. |
| T-23-01-02 | Information disclosure | Full DSNs (with credentials) stored in `tenants.dsn` | accept | Same-box loopback MariaDB, app-user-only access, no SSL by existing rationale (db/index.ts lines 13-15). DSNs live in the platform DB behind the app user — same trust level as `.env.local` today. Per-tenant DB users are a documented Phase-C hardening (ARCHITECTURE.md open question 2), not this phase. |
| T-23-01-03 | Denial of service | Non-idempotent migration corrupting/duplicating tables on re-run | mitigate | INFORMATION_SCHEMA `tableExists` guard on every CREATE; Task 3 proves a second run applies 0 changes. |
| T-23-01-04 | Repudiation | Silent partial apply leaving the fleet in an unknown schema state | mitigate | `applied[]`/`skipped[]` summary + `SHOW CREATE TABLE` echo + `process.exit(1)` on any fatal — the phase21 discipline. |

No HIGH-severity residual. T-23-01-02 (accepted) matches the project's standing loopback-DB trust model.
